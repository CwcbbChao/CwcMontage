# 双缓冲槽 Playables 混音拓扑设计

在 Unity 动画底层开发中，`Playables API` 提供了远超传统 Animator 的灵活性，但如果使用不当，极易引起严重的性能惩罚。

---

## 传统动态连接拓扑的弊端

很多基于 Playables 的动作插件在实现动作融合（CrossFade）时，通常采用“动态图构建”策略：
- 每次播放新动作，就调用 `playableMixer.AddInput()` 动态追加一个输入端口。
- 动作淡出完成后，调用 `playableMixer.DisconnectInput()` 断开节点并调用 `Destroy()`。
- 或者将数组元素前移填补空缺。

### 为什么在高性能动作游戏中必须杜绝此做法？
1. **内部重新拓扑开销**：频繁的 `ConnectInput` / `DisconnectInput` 会促使 Unity C++ 底层重新计算 PlayableGraph 的求值拓扑与遍历顺序，引发 CPU 微卡顿。
2. **GC 内存分配**：动态创建 Playable 节点并交给 C# 托管层管理容易产生对象分配与析构。
3. **端口索引漂移**：动态增删容易导致 Mixer 端口号发生错位，造成错误的权重计算。

---

## CwcMontage 的解决方案：预分配双插槽 (Double-Buffered Slots)

`CwcMontage` 在角色初始化时，为每个图层预分配好固定的双插槽拓扑结构：

```
                    +---------------------------+
                    | AnimationPlayableOutput   |
                    +-------------+-------------+
                                  |
                    +-------------v-------------+
                    | AnimationMixerPlayable    | (固定 2 个输入端口)
                    +----+-----------------+----+
                         |                 |
                [Input 0: 槽位 A]    [Input 1: 槽位 B]
                         |                 |
                    +----v----+       +----v----+
                    | Clip A  |       | Clip B  |
                    +---------+       +---------+
```

### 运行机制：双插槽交替 (Ping-Pong)

1. **初始态**：
   - 槽位 A 处于激活态（权重 $W_A = 1.0$），正在播放当前攻击动作。
   - 槽位 B 处于空闲静默态（权重 $W_B = 0.0$）。
2. **触发 CrossFade 过渡**：
   - 外部请求以 $0.2s$ 淡入播放下一个连击动作。
   - 系统将新动作绑定到空闲的**槽位 B**，并将槽位 B 的播放时间重置为 0。
   - 在接下来的 $0.2s$ 内，内部时钟平滑计算过渡权重：
     $$W_B = \text{SmoothStep}(t / 0.2)$$
     $$W_A = 1.0 - W_B$$
3. **过渡结束**：
   - $W_B$ 达到 $1.0$，$W_A$ 归零。
   - 此时槽位 B 成为当前活跃槽位，槽位 A 自动释放为空闲槽位，等待下一次切换。

---

## 核心收益

- **零 GC 开销**：在整个动画播放与 CrossFade 过渡期间，PlayableGraph 无需频繁创建/销毁托管对象，0 运行时 GC 内存分配。
- **稳定的图拓扑**：避免了在运行时高频增删 Mixer 输入端口，消除了 Unity C++ 底层重新计算 PlayableGraph 遍历拓扑的 CPU 开销。
- **状态清晰可控**：仅通过两个插槽的状态即可完整追踪新旧动作的淡入淡出，便于调试与问题排查。
